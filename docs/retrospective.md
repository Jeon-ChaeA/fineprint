## 2. 잘된 것

1. **문제에서 시작했다.** 앱 관찰과 설문(39명)으로 "요약은 있는데 기억에 안 남는다", "당황하는 건 숫자가 아닌 조건이다"를 먼저 확인하고 기능을 정했다. 그 뒤 사용성 테스트 두 번에서 D-008은 한 번도 흔들리지 않았다.
2. **처음 보는 문항으로 쟀다.** 버전을 고치기 전에 새 문항을 먼저 만드는 습관 덕분에 두 번 잘못된 결론을 피했다.
   - 1.2 점검 단계: 기존 문항에서는 좋아 보였지만 처음 보는 문항에서 효과가 0이었다.
   - 안전장치 정규식: 72문항에서는 완벽했지만 처음 보는 질문에서는 판단 불가를 4/15만 잡았다.
3. **신뢰 장치를 코드에 뒀다.** 검색, 교차 참조 확인, 인용 검증, 안전장치가 코드라서 모델을 Claude에서 Gemini로 바꿔도 지어낸 인용이 0건이었다. 모델이 약해도 "틀린 단정"은 막을 수 있었다.
4. **원자료를 공개하지 않는 원칙을 끝까지 지켰다.** 약관 원문은 비공개 레포, 설문·테스트 응답 원본은 시트에만 두고 레포에는 집계만 올렸다. 배포 서버도 토큰으로 비공개 레포에서 받는다.
5. **사람이 판단한 지점을 남겼다.** 채점 확정, 방향 결정, 모델 선택은 모두 전채아가 했고 devlog의 "사람이 판단한 지점"에 적었다.

## 3. 아쉬운 것

1. **사람 테스트가 약하다.** 1차 5명은 모두 대출 경험이 없었고(1명은 진행자 본인), 2차는 AI 가상 사용자였다. 제품의 주 사용자인 대출 경험자의 반응을 아직 못 봤다.
2. **실시간 답 품질이 평가 결과보다 낮다.** 평가는 Claude로 O 70이었지만 공개 서버는 무료 Gemini로 O 39다. 공개된 쪽이 약한 쪽이다. 비용 결정이었지만 PRD의 답 정확도 목표(80%)와 차이가 크다.
3. **AI 채점에 기댔다.** 1.1~1.4는 전채아가 채점지를 확인했지만, 1.5 이후와 Gemini 비교는 AI 블라인드 채점이 중심이다. 같은 답을 다시 채점하면 1~3문항이 갈린다.
4. **작업 비용 관리가 늦었다.** 하위 에이전트가 파일 내용을 그대로 옮겨 쓰다 95만 토큰을 썼고(10-20), 사용량 한도에 네 번 걸렸다. 무료 Gemini는 3.8-flash가 한도·시간 초과로 평가를 끝내지 못했다.
5. **일정**: 3주 계획이 4주가 됐다. 에이전트를 1.6까지 6번 고친 것이 컸다. 1.4 이후는 오름 폭이 작았다(O 63 → 70).

## 4. 배운 것

- **"모르면 모른다"가 가장 비싼 기능이었다.** 강한 모델은 지시만으로 판단 불가를 지켰지만, 약한 모델은 정규식 + 분류기 + 코드 안전장치가 필요했다. 그리고 안전장치는 과적합되기 쉽다(72문항 10/10 → 처음 보는 질문 4/15).
- **실패는 대부분 검색에서 시작했다.** 1.0 감점의 절반, 2차 테스트의 P1(금리인하요구권), J01(원금부터 줄이기)이 모두 사용자 말과 약관 말의 차이였다. 용어 사전 몇 줄이 프롬프트 수정보다 효과가 컸다.
- **원문도 함정이다.** 같은 은행의 상품설명서와 약정서가 다르게 적고, 교차 참조가 다른 조를 가리키기도 한다. "확인 필요"는 약점이 아니라 기능이다. 이 발견이 기업용 제안서의 모듈 ③(문서 정합성 점검)이 됐다.
- **'판단할 수 없음'만으로는 부족하다.** 1차에서는 믿음을 줬지만(3/4), 2차 가상 사용자는 "둘 다"(믿음과 답답함)였다. 그다음 할 일을 함께 줘야 한다.
- **평가는 한 번 돌려서는 모른다.** 같은 버전·같은 문항에서 3회 등급이 갈린 경우가 124개 중 24개였다. 버전 비교는 3회 다수결 + 섞어서 블라인드로.

## 5. AI와 사람의 역할

| 단계 | AI가 한 일 | 사람(전채아)이 한 일 |
|---|---|---|
| 조사 | 화면 녹화 프레임 정리, 설문 집계, 공시 문서 위치 조사 | 앱 직접 사용·녹화, 설문 배포, 결과 해석과 방향 결정 |
| 평가 | 질문셋 초안, 원문 대조, 블라인드 1차 채점 | 채점 기준(필수·선택) 결정, 채점지 확정, 우선순위 |
| 개발 | 검색·에이전트·화면·안전장치 코드, 배포 설정 | 계정 로그인, 토큰·키 입력, git push, 모델·공개 범위 결정 |
| 테스트 | 테스트 설계, 가상 사용자 연기, 결과 정리 | 지인 모집, 1차 응답, 반영 범위 결정 |

AI가 혼자 결론을 낸 곳은 없게 했다. 다만 AI가 만든 질문셋을 AI가 채점하는 구조는 같은 쪽으로 치우칠 수 있다. 다음 사이클에서는 사람이 쓴 질문을 섞는다.

## 6. 다음 사이클에 가져갈 것

1. **사람 테스트를 일찍, 대상 사용자로.** 프로토타입 직후 대출 경험자 테스트를 먼저 잡는다. PRD 실험 1을 이번 사이클의 마무리로 한다.
2. **공개하는 모델로 평가한다.** 평가 모델과 서비스 모델이 다르면 평가 결과가 실제를 말해 주지 않는다. 처음부터 쓸 모델을 정하고 그 모델로 잰다.
3. **안전장치는 처음 보는 질문셋과 함께 만든다.** 규칙을 만든 질문셋과 확인할 질문셋을 처음부터 나눈다.
4. **에이전트 개선은 멈출 기준을 정한다.** 예: 처음 보는 문항에서 2회 연속 오름이 1문항 이하면 멈추고 사용자 쪽으로 넘어간다.
5. **다음 상품은 신용카드.** 혜택 조건과 제외 항목. 코어(분할, 검색, 인용 검증, 안전장치)는 그대로 쓰고 용어 사전과 질문셋만 새로 만든다.

## 7. 사이클 2(신용카드)를 가볍게 마친 뒤: 코어를 다시 쓴다는 것

사이클 2는 3주 계획을 하루 분량으로 줄여 "코어가 다른 상품에 붙는가"만 확인하고 멈췄다(전채아 결정). **검색·인용 검증·안전장치·화면은 한 줄도 갈아엎지 않고** `product="card"` 모드와 카드사 이름만 더해 붙었고, 대출 쪽 검색 결과는 157개 질문 모두 그대로였다. 처음 보는 카드 질문 24개에서 정답 문구가 근거 목록에 들어온 것이 23개다([결과](../eval/results-card-v1.md)). 새로 만든 건 코어 바깥이었다. 상품설명서는 좌우 두 면과 표로 돼 있어서 표를 행 단위로 읽는 분할기가 필요했고, BC카드 약관은 웹 페이지라 텍스트 입력을 받게 했다. 배운 것은 세 가지다. ① **문서 처리가 가장 큰 위험이었다.** 병합 칸을 채우는 코드가 다른 행의 숫자를 복사해 넣었는데, 이건 모델이 아니라 내 코드가 숫자를 지어낸 것이다. 처리 결과의 숫자를 원문과 세어 비교하는 검사가 없었으면 못 찾았다. 글자가 안 나와 스캔본으로 착각한 PDF도 원인은 한글 CMap이었다. ② **이름이 비슷한 상품은 다른 상품이다.** 15만원 vs 20만원을 "문서끼리 다르다"로 적을 뻔했다. '확인 필요'를 달기 전에 상품명부터 대조한다. ③ **용어 사전 효과는 또 착각이었다.** 내가 쓴 점검 질문에서는 순위가 올랐지만 처음 보는 질문에서는 그대로였다. 사이클 1의 교훈을 알면서도 같은 함정에 한 번 더 들어갔고, 처음부터 질문셋을 나눠 둔 덕분에 바로 드러났다. 카드 요약 12줄은 숫자 원문 대조만 했고 사람 확정을 기다린다. 답 품질 평가(모델 답 채점)와 카드 사용자 테스트는 하지 않았으므로, 카드 탭은 베타로 둔다.
